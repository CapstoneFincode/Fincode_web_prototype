# 성능 평가

정상 이메일 자동 채점, 단일 모델 평가와 2~5개 모델 비교 실행을 운영 Railway API와 기존 Sites 웹에 배포했다. 합성 정상 이메일 100건의 정상 라벨과 기준 요약은 모두 검토 완료 상태다. 방어 기능은 프로젝트의 최종 단계이며 이번 평가 실행은 OFF만 지원한다. 배포 버전은 [DEPLOYMENT.md](DEPLOYMENT.md)에 기록한다.

## 메뉴와 평가 대상

왼쪽 **성능 평가** 아래에 **이메일 요약기** (`#email`), **단일 모델 성능 평가** (`#single-evaluation`), **모델 별 비교** (`#comparison`)를 둔다. 원래 이메일 요약기의 한 건 요약·기준 요약 별도 보기·사용량 확인은 유지한다.

평가 대상은 `ground_truth_set/v1`의 합성 정상 이메일 100건이다. DB의 모든 정상 이메일을 무조건 포함하지 않고 원본 제목·본문과 일치하는 최신 등록 버전을 연결한다. 기존 UI 예시 5건은 제외한다. 동일 원문의 활성 항목이 중복되면 선택을 중단하고 정리를 안내한다.

전체 100건 또는 소량의 분산 표본으로 실행할 수 있다. 단일 평가는 모델 1개, 비교는 서로 다른 모델 2~5개를 선택한다. 이메일·모델 조합마다 한 번 호출하며 실행 전에 총 호출 수를 표시한다. 한 평가의 최대 호출 수와 대기·실행 중 성능 평가 전체 상한은 각각 500회다.

## 실행·저장·비교

- 모든 모델에 같은 이메일·요약 지시·출력 제한을 적용한다. 이메일마다 모델의 실행 순서를 회전해 특정 모델이 항상 먼저 실행되는 것을 줄인다.
- 기존 서버 워커와 실험 저장 구조를 활용한다. 실험 간 순환 배정으로 긴 평가가 다른 공격 실험의 대기열을 독점하지 않도록 한다. 기존 즉시 이메일 요약은 별도 실행 경로다.
- 이메일과 기준 정답의 ID·버전·내용, 채점기 버전, 입력 지시·설정을 실행 시작 시 고정한다. **기준 정답은 모델 요청에 포함하지 않는다.**
- 진행률·이력·집계와 개별 응답 상세를 구분해 조회한다. 화면 이동/새로고침 후 DB 기록을 다시 볼 수 있다. 원문·기준 요약·생성 요약·채점 근거·실제 반환 모델을 함께 확인한다.
- 모델별 유사도, 핵심 정보 자동 확인, 응답시간과 토큰 사용량을 나란히 표시한다. 모든 모델에서 채점이 완료된 공통 이메일 표본에 대한 비교도 제공한다. 완료율과 오류·취소 건수를 함께 본다.
- API 실패는 품질 0점으로 처리하지 않으며 제공되지 않은 토큰·측정값은 0으로 추정하지 않는다. 품질 점수를 임의의 종합 순위나 정답률로 바꾸지 않는다.
- 중단은 아직 호출하지 않은 작업만 취소한다. 이미 실행 중인 요청은 응답/사용량을 저장한다. 불확실한 제출이나 실패한 모델 호출은 자동 재시도하지 않는다. 인증 오류·한도 오류·연속 실행 오류에는 후속 요청을 중단한다.

## 채점과 검토 상태

별도의 채점용 LLM을 호출하지 않는다. 한국어와 영문을 보존하는 문자 기준 ROUGE-L 유사도와 보수적인 핵심 정보 확인을 분리한다. 유사도는 사실 정확도가 아니며, 자동으로 확인되지 않은 핵심 정보도 곧바로 오답이라는 뜻은 아니다. 자세한 처리 기준·한계·버전은 [SUMMARY-QUALITY.md](SUMMARY-QUALITY.md)에 기록한다.

정상 라벨이 검토 완료이고 사용 가능한 기준 요약이 있어야 제출할 수 있다. 기준 요약이 draft이면 **초안 기준 예비 평가**로 표시하고 실행 당시 상태를 고정한다. 이후 정답의 승인 상태나 내용이 바뀌어도 과거 결과의 평가 조건을 바꾸지 않는다.

2026-11-09 사용자 요청에 따라 합성 100건의 정상 라벨을 먼저 검토 완료로 처리한 뒤, 새 API 배포 후 기준 요약 100건도 승인했다. 라벨 승인 시 이메일은 버전 2가 되었고, 이후 기준 요약 승인에서는 이메일·정답의 ID와 버전 및 원문·정답·핵심 정보를 유지했다. 승인 도구의 재조회에서 정상 라벨·기준 요약 각각 100건과 내용·다른 데이터 보존을 확인했다. [승인 범위·점검 내용](DATASET-REVIEW.md), [라벨 승인 기록](verification/2026-11-09-normal-label-approval.json), [최종 정답 승인 기록](verification/2026-11-09-ground-truth-approval.json)을 참고한다.

방어 선택 항목은 구현 예정으로 남기고 OFF 외에는 실행할 수 없다. 방어 오차단률과 방어 전후 성능 저하 비교는 방어 기능을 구현하는 최종 단계에서 연결한다.

## 데이터와 검토 상태

- 원본: `datasets/ground_truth_set/v1/emails.json`, `GT-SYN-001`–`GT-SYN-100`.
- 원본 SHA-256: `f8818c7418dc99fe54feb84e63fd5d51430bfeb93362f1e841461cac03a2889d`.
- 기존 정상 예시는 보존하고 합성 100건을 추가한다. 운영 자동 seed에는 넣지 않는다.
- 기존 정상 이메일 API에 제목, 본문, 기준 요약 초안, 필수 핵심 정보와 `reviewStatus=pending`을 전달한다. 서버는 정상 라벨, 합성 출처와 기준 요약 `draft` 상태를 저장한다.
- 최초 등록 당시 정상 라벨은 pending, 기준 요약은 draft였다. 이후 사용자 요청에 따른 정상 라벨 승인과 사람의 개별 검수 여부는 구분한다. 최신 운영 승인 범위는 위 설명과 DATASET-REVIEW.md를 따른다.
- 원본 ID와 서버가 생성한 ID/UUID/버전은 등록 보고서로 연결한다. 유형, 난이도, 원문 근거, 검토 메모 등 확장 메타데이터는 원본 파일에 보존한다.
- 운영 GET API는 합성 출처를 화면용 `user`로 표시하고 기준 요약 ID·버전·검토 상태·승인 메모·내용 해시를 함께 반환한다.

## 운영 등록 절차

`scripts/import-ground-truth.py`는 기본적으로 읽기 전용 사전 검사를 한다. `--apply`를 명시할 때만 기존 `/api/data/normal`에 없는 항목을 순차 등록한다. 접근 토큰은 숨김 입력으로 받고 파일/출력/보고서에 저장하지 않는다.

```bash
python scripts/import-ground-truth.py datasets/ground_truth_set/v1/emails.json \
  --site https://fincode-security-lab.xogus090721.chatgpt.site \
  --report /tmp/fincode-ground-truth-dry-run.json
```

검사 결과를 확인한 뒤 같은 명령에 `--apply`를 추가하고 별도의 등록 보고서 경로를 지정한다.

등록 전 전체 데이터 해시와 충돌을 검사한다. 같은 제목·본문의 항목이 이미 있으면 기준 요약·핵심 정보·검토 상태까지 일치할 때만 재사용한다. 응답이 불확실한 POST는 자동 재시도하지 않고 중단한다. 재실행 전 읽기 전용 검사로 저장 여부를 확인한다. 이 방식은 HTTP 항목별 등록이며 전체 100건을 묶은 DB 트랜잭션은 아니다. 한 번에 한 담당자만 등록 작업을 실행한다.

등록 후 원본 100건을 대조하고 기존 정상 이메일, 공격 시나리오, 카테고리의 내용 보존과 기존 실험 ID의 존재를 확인한다. API 실험 목록은 최신 100건까지이므로 목록 수를 전체 DB 실험 수로 해석하지 않는다. 모델 실행·자동 채점·과거 결과 변경은 수행하지 않는다.

## 다음 단계

운영 배포와 기준 요약 100건의 승인을 마쳤다. 이번 배포 검증에서는 유료 모델을 호출하지 않았다. 사용자가 5건 또는 10건의 소량 평가로 API 한도와 선택 모델의 지원 여부를 확인한 뒤 전체 비교를 진행할 수 있다. 기준 정답 및 자동 확인 규칙의 사람 검수와 개선은 계속할 수 있다.

팀 로드맵은 공격 실험 버그 수정 → 파일 업로드 → 공격 시나리오 데이터 확충 → 보안 기능 구현이다. 모델 성능 평가는 이 로드맵과 병행하며 방어 기능은 마지막 단계에 연결한다.
