# 첨부파일 요약·간접 공격

첨부 기능의 최초 구현은 2026-11-11 기준 `main`의 `c4b0bd2`(공격 UI 예시 정리 포함)를 기반으로 UI에서 재검증한 뒤 PR #4로 main에 병합했다(병합 `360938a`, 검증 소스 `cbc9bf2`). 이후 개발 기준은 main이다. 당시 운영 배포는 `1ba7ba3`에서 완료했고 비공개 S3 원본 저장·추출·실제 모델 호출을 확인했다. [당시 운영 검증 기록](verification/2026-11-11-attachments-release.json)을 참고한다. 아래 과거 검증 절은 이메일 요약의 DB 저장 중단 이전 기록이며, 현재 소스 변경의 배포 완료를 뜻하지 않는다. 프롬프트 인젝션 방어는 OFF이며 ON 기능은 후속 단계에서 구현한다.

## 사용 흐름

이메일 요약기에서 파일을 선택하면 원본을 업로드하고 텍스트를 추출한다. 파일별 완료·오류 상태와 추출 텍스트를 확인한 뒤 모델을 선택해 요약한다. 본문이 없어도 추출 완료 파일만으로 실행할 수 있다. 파일 제거는 현재 입력에서 제외하는 동작이며 저장된 원본이나 과거 실행을 삭제하지 않는다.

현재 이메일 요약기는 결과를 현재 화면에만 반환한다. 요약 실행의 입력·출력·사용량·실행 기록은 DB에 추가하지 않으며 새로고침 후 DB에서 복원하지 않는다. 업로드 원본·추출 텍스트·메타데이터의 보관은 이 요약 실행 기록과 별개로 유지한다.

데이터 관리의 공격 시나리오에서 간접 인젝션 → 첨부파일 추출문을 선택하면 같은 업로드 UI가 나타난다. 선택 사항인 이메일 본문과 파일을 함께 저장한 뒤 공격 실험의 간접 경로에서 해당 카테고리를 선택한다. 파일이 연결되지 않은 과거 시나리오는 실행 대상에서 제외한다. 파일 텍스트는 사용자 메시지에만 들어가며 시스템 지침을 바꾸지 않는다.

첨부 공격 실험을 실행하면 파일 ID·이름·원본 SHA-256·추출 텍스트 SHA-256·추출 방법·버전·추출 텍스트와 실제 전송 메시지를 DB에 고정한다. 나중에 시나리오의 파일을 바꾸어도 이미 대기 중이거나 완료된 실행의 입력은 바뀌지 않는다. 정상 응답 확인·성능 평가의 기존 입력 스냅샷과 실행 결과 저장도 유지한다. 이메일 요약기는 서버에서 파일 ID로 읽은 추출 결과로 메시지를 구성해 바로 호출하며 메시지를 별도로 저장하지 않는다. 두 흐름 모두 클라이언트가 제공한 임의 추출 텍스트는 신뢰하지 않는다.

## 형식과 한도

| 형식 | 처리 | 한계 |
| --- | --- | --- |
| TXT | UTF-8, BOM 있는 UTF-16, CP949 | 인코딩 오류를 숨기거나 문자를 임의 제거하지 않음 |
| PDF | pypdf, 텍스트 없는 페이지는 Poppler + Tesseract | 최대 20페이지, OCR 오인식 가능 |
| DOCX | python-docx 문서 구조 순회 | 본문·표, 문서에 삽입된 이미지 OCR 제외 |
| PPTX | python-pptx | 최대 20슬라이드, 텍스트 상자·그룹·표, 이미지 OCR 제외 |
| PNG/JPG/JPEG | Pillow + Tesseract 한국어·영어 | 최대 2,000만 화소, 단일 프레임 |
| HWP | pyhwp XML 문서 구조 순회 | 일반 HWP 5.x 본문·표; 암호·배포용·DRM 문서는 안내 후 거절 |
| HWPX | ZIP/XML 문서 구조 순회 | 본문·표, 외부 DTD 및 비정상 압축 구조 거절 |

- 파일당 10 MiB, 입력당 최대 5개. 추출 텍스트는 파일당 50,000자, 모델 사용자 입력은 제목·파일명·구분자까지 포함해 60,000자 이하이다.
- 한도 초과 시 내용을 잘라 실행하지 않고 오류를 표시한다. 화면과 서버는 Unicode 코드포인트를 기준으로 길이를 센다.
- DOC/PPT는 DOCX/PPTX 또는 PDF로 변환해 업로드한다. 비가시 문자와 원문 공백은 보존하며, 문단·표·페이지를 구분하는 개행·탭·표시가 추가될 수 있다.
- HWP 기본 `hwp5txt`는 표 내용을 생략하므로 사용하지 않는다. 검증한 HWP 두 파일은 XML 방식으로 본문과 표를 읽었다.
- 텍스트와 이미지가 섞인 PDF는 텍스트가 있는 페이지의 이미지 부분을 추가 OCR하지 않는다. 누락 가능성을 경고한다. DOCX/PPTX/HWP/HWPX 내부 이미지도 별도 OCR하지 않는다.
- OCR은 원문과 완전히 같다고 보장하지 않는다. 스캔 PDF 테스트에서 `회의`가 `외의`로 읽힌 사례가 있어 미리보기 확인이 필요하다. 특히 OCR 결과를 이용하는 공격은 원본 이미지와 실제 추출 입력을 함께 검토한다.
- 별도 추출 프로세스의 제한: 45초, 주소 공간 384 MiB, CPU 30초. 한 API 프로세스에서 동시에 한 파일만 추출하며 초과 요청은 429로 안내한다. API 키와 DB 연결 문자열을 파서 프로세스 환경으로 전달하지 않는다.

## API와 저장

- `POST /api/attachments`: `multipart/form-data`, `file` 필드 하나. 성공 `201 {attachment: ...}`에 ID·메타데이터·추출 텍스트를 반환한다.
- `GET /api/attachments/{id}`: 성공한 추출 결과 조회.
- `POST /api/summarize`: `attachments: [UUID, ...]`. 서버가 기존 추출 결과를 읽기 전용으로 조회해 입력을 구성한다. 요약 실행·입력·출력·모델 호출 기록을 DB에 생성하지 않으며 성공 응답은 `database: {saved: false, mode: "transient"}`를 포함하고 `experimentId`/`runId`는 반환하지 않는다. 첨부 요약에는 기존 첨부 결과를 읽을 DB 연결이 필요하다.
- 공격 시나리오 등록·수정: `attachmentIds: [UUID, ...]`, `vector: indirect`, `channel: attachment`. 데이터 목록에는 파일 메타데이터만 반환한다.
- 일반 정상 이메일 실험은 별도 `attachments` 입력을 받지 않는다. 저장된 정상 평가 입력이 첨부파일로 오염되지 않게 유지한다.
- Worker 프록시는 `/api/attachments`의 POST에만 multipart를 허용한다. boundary·바이너리를 보존하고 실제 스트림을 10 MiB + 64 KiB로 제한한다. 다른 요청은 기존 JSON/200 KB 제한을 유지한다.
- `007_attachments.sql`은 기존 첨부 테이블을 확장하고 버전별 시나리오와 파일의 순서 있는 연결을 추가한다. 기존 자료와 실행 기록을 삭제하지 않는다.

원본은 저장소에, 추출 텍스트와 메타데이터는 PostgreSQL에 보관한다. 개발 Compose는 별도 영구 볼륨을 사용한다. 운영 환경에서는 비공개 S3 호환 저장소를 설정해야 하며 로컬 디스크 모드는 거절한다. 설정이 없으면 업로드 기능만 비활성화된다. 기존 본문 요약·성능 평가는 계속 사용할 수 있다.

기존 이메일 요약 실행과 첨부 원본을 삭제하지 않는다. 과거 요약은 실험 결과 목록·집계에서 제외하지만 ID별 상세 조회는 유지한다. 이번 저장 정책 변경에는 새 마이그레이션·데이터 삭제·DB 또는 화면 최적화를 포함하지 않는다. 결과 조회 범위는 [RESULTS.md](RESULTS.md)를 참고한다.

환경변수는 `.env.example`을 참고한다. 운영에 추가할 항목은 `FINCODE_ATTACHMENT_STORAGE=s3`, `FINCODE_ATTACHMENT_S3_ENDPOINT`, `FINCODE_ATTACHMENT_S3_BUCKET`, `FINCODE_ATTACHMENT_S3_ACCESS_KEY_ID`, `FINCODE_ATTACHMENT_S3_SECRET_ACCESS_KEY`, 선택 사항인 `FINCODE_ATTACHMENT_S3_REGION`이다. 키는 서버 환경변수에만 둔다.

`FINCODE_ATTACHMENT_S3_URL_STYLE`은 Bucket에 맞춰 `path`, `virtual`, `auto` 중 하나로 설정한다. 미설정 시 기존 저장소와의 호환성을 위해 `path`를 유지한다. 신규 Railway Bucket의 자격증명에 `urlStyle=virtual-host`가 표시되면 이 설정에는 `virtual`을 사용하고, endpoint에는 Bucket 이름을 붙이지 않은 제공된 기본 HTTPS 주소를 넣는다. 지원하지 않는 값은 업로드 설정을 비활성화하며 기존 본문 요약은 유지한다. 설정 완료 표시는 실제 저장소 연결 검사를 대신하지 않으므로 소량 업로드로 확인한다.

## 구현·병합 단계 검증 (운영 배포 이전 기록)

- 최신 main 통합 후 JavaScript 149/149, Python 166/166 통과. Python은 임시 네이티브 PostgreSQL 16.2와 실제 HWP fixture를 포함하며 skip이 없다.
- 브라우저에서 TXT 업로드 → 추출 완료 → 첨부만 요약 → DB 기록, 간접 첨부 시나리오 등록 → 해당 카테고리만 실행 → 결과의 실제 메시지 확인을 수행했다. 모델은 명확히 표시한 모의 응답이며 유료 모델 API는 호출하지 않았다.
- 실제 HWP 2개, 한글·영문 PNG/JPEG, 스캔 PDF를 추가 검증했다. 개인 HWP 원본과 추출 내용은 저장소에 포함하지 않았다.
- 일반 재실행: `node --test tests/*.test.mjs`; `FINCODE_TEST_DATABASE_URL`을 폐기 가능한 PostgreSQL에 설정한 뒤 `python -m unittest discover -s backend/tests -v`. 실제 HWP는 선택 변수 `FINCODE_HWP_TEST_FILE`에 별도 로컬 파일을 지정한다.
- 테스트에는 실제 저장된 원문과 모델 입력 일치, 시나리오 수정 후 기존 입력 보존, 정상 평가 입력 보호, 한도·실패·취소·동시 업로드, 직접/간접 분리, 이모지·비가시 문자·HTML 안전 표시를 포함한다.
- Docker 빌드와 실제 S3 입출력은 이 환경에서 검증하지 않았다. Docker에는 Tesseract 한국어·영어와 Poppler를 설치하도록 추가했다. 운영 반영 전에 Bucket 설정, Docker 빌드, migration 007, 실제 소량 업로드를 확인해야 한다.
- `pyhwp==0.1b15`의 라이선스는 AGPL-3.0-or-later이며 설치 패키지의 COPYING에 포함된다. 추출기는 이 라이브러리를 사용한다. 의존성과 배포 구성 검토 시 이 항목을 포함한다.

## 추가 재검증 — 2026-11-11 (운영 배포 이전 기록)

- 비정상적으로 긴 `Content-Length` 헤더가 500을 발생시키던 문제를 수정했다. 큰 숫자는 정수 변환 없이 413으로 거절하며, 선행 0이 많은 정상 크기도 처리한다.
- 이메일 본문의 표시 글자 수를 코드포인트 기준으로 통일했다. HTML maxlength의 UTF-16 단위 잘림을 제거하고, 30,000자를 넘으면 원문을 보존하면서 오류 표시·실행 차단을 한다.
- 수정 후 JavaScript 149/149, Python 166/166, 웹 빌드와 정적 자산 일치 검사를 다시 통과했다. 실제 HWP 2개와 PNG/JPEG/스캔 PDF 추출도 재확인했다.
- 폐기 가능한 PostgreSQL 16.2에서 001–006 스키마에 합성 기존 데이터를 채운 뒤 007을 적용하고 재실행했다. 기존 13개 테이블·17개 행의 기존 필드가 모두 보존됐고, 기존 첨부의 3개 상태 및 새 기본값, 새 연결과 제약 7종, DB health를 확인했다.
- 실제 S3·Docker 실행·유료 모델 호출은 여전히 미검증이며 운영 DB와 main은 변경하지 않았다.

## 최초 운영 배포 검증 — 2026-11-11, 이메일 요약 저장 중단 이전 기록

- Railway 비공개 S3 Bucket을 연결하고 `FINCODE_ATTACHMENT_S3_URL_STYLE=virtual`로 운영 입출력을 확인했다. Docker 빌드·시작과 migration 007 적용 후 DB/첨부 기능이 정상 활성화됐다. 원본 객체의 비인증 조회는 403이다.
- S3 설정 수정 후 전체 Python 168/168(skip 없음), 프런트엔드 빌드를 통과했다. 첨부 통합 JavaScript 검증은 149/149다.
- 합성 파일 9건(7개 형식군, 8개 확장자)의 실제 업로드·추출·재조회와 원본 SHA-256을 확인했다. HWP는 최소 OLE/HWP 5.x 합성 파일의 추출문을 정확히 대조했으며 한컴 GUI 표시를 확인한 것은 아니다. 개인 HWP 자료는 운영에 업로드하지 않았다. `.jpeg` 별도 사례는 없고 동일 처리 경로의 `.jpg`를 시험했다.
- 실제 BAZE `gemini-3.5-flash-lite`로 TXT+HWP 요약과 첨부 간접 공격을 각각 1회 실행했다. 응답·사용량·실행 당시 입력이 DB에 저장됐고 간접 공격의 자동 판정도 완료됐다. 모델이 목표 표식을 출력하지 않아 검증 공격은 실패로 판정됐다. OFF가 공격 성공을 보장하지 않는다는 점을 보여주는 한 사례이며 공격 성공률 측정은 아니다.
- 검증용 공격 시나리오는 보관 후 활성 목록에서 제외했다. 합성 파일 10건과 실행 이력 2건은 검증 기록으로 남겼다. 기존 정상 105건·공격 41건·카테고리 7개 및 확보한 최근 실험 100개/실행 350건·성능평가 기록은 배포 전 값과 일치했다. 검증 중 별도로 등록된 사용자 공격 9건도 보존했다.
- 운영 정적 자산 7개는 검증 중 추가된 새로고침 버튼 이동까지 포함한 main `f6c8102`와 일치한다. 기존 사이트 접근 범위와 환경 설정을 유지했다. 운영 인증 API를 검증했지만 로그인 후 브라우저 클릭 QA는 반복하지 않았다. OCR 미리보기 확인과 위 형식별 지원 한계는 계속 적용된다.

## 방어 OFF 기준과 향후 ON 비교

현재 첨부 텍스트에는 공격 문구 탐지·삭제·정규화를 적용하지 않는다. 추출된 텍스트를 파일 출처 라벨과 함께 user 메시지에 넣으며, 시스템 프롬프트에는 일반 이메일 요약 지시만 있다. OFF는 프로젝트가 추가 방어를 적용하지 않는다는 뜻이며 모델이 공격을 반드시 따르는 것은 아니다.

파일 처리·원본 저장의 보호 조건은 ON/OFF 양쪽에서 동일하게 유지한다. 향후 ON은 같은 추출 결과에 선택한 방어를 적용하는 단계로 추가한다. 공격·성능 평가 실험에서는 원본 추출문·방어 후 입력·방어 버전·차단 이유·실제 모델 입력을 기록해 공격 성공률뿐 아니라 정상 첨부의 오차단·요약 품질·응답시간·토큰을 비교한다. 이는 향후 실험 설계이며 현재 이메일 요약기의 임시 결과 저장 정책을 바꾸는 기능은 아니다. 업로드/추출 실패, 방어 차단, 모델 거부를 구분한다.
