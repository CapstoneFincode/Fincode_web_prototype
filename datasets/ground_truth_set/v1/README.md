# 합성 정상 이메일 평가 후보 — v0.1.0-draft

합성 정상 이메일 **100건**을 보관하는 검토용 데이터 세트다. 모두 AI가 작성한 가상 이메일이며, 사람이 정상 여부와 기준 요약을 승인하기 전의 **후보 초안**이다. `expectedLabel=normal`은 생성 목표이고 검증 완료 사실을 뜻하지 않는다.

- 브랜치: `ground_truth_set`
- 기준 main 커밋: `7d62fa55a83f55e3f3900a874103a57a8ff996fd` (자동 공격 판정 기능 통합 이후)
- 생성일: 2026-11-04 (Asia/Seoul)
- 실제 이메일·사용자 개인정보를 수집하거나 생성 입력으로 사용하지 않았다. 등장 조직·인물·일정·거래는 가상이다.
- 2026-11-04에는 `ground_truth_set` 브랜치에 파일만 보관했다. 2026-11-09 main의 운영 등록 절차와 현재 적용 범위는 [모델 평가 준비 문서](../../../docs/MODEL-EVALUATION.md)를 따른다. 원본 이메일과 정답 초안은 변경하지 않는다.
- 모든 항목은 `reviewStatus=pending`, `referenceReviewStatus=draft`다. 인간 검토 완료 건수는 **0건**이다.

## 구성과 생성 조건

실제 사용자 이메일의 분포를 추정한 무작위 표본이 아니다. 비교 실험에서 다양한 정상 입력을 다루도록 **유형별 수량을 설계한 합성 표본**이다.

| 유형 | ID | 건수 |
| --- | --- | ---: |
| 일정·회의·예약 (`meeting_schedule`) | GT-SYN-001–020 | 20 |
| 업무 요청·제출·협업 (`work_request`) | GT-SYN-021–040 | 20 |
| 공지·운영·정책 안내 (`notice_policy`) | GT-SYN-041–060 | 20 |
| 문의·답변·지원 (`inquiry_reply`) | GT-SYN-061–080 | 20 |
| 신청·주문·배송·정산 (`transaction_logistics`) | GT-SYN-081–100 | 20 |

각 유형은 일반 정상 메일 16건과 오탐을 살펴볼 정상 메일(`hard_benign`) 4건으로 구성한다. `hard_benign`은 권한·보안·비밀번호·업무 자료 삭제 등의 표현이 등장하지만 수신자의 정상 업무를 위한 내용이며, 요약 모델의 지시를 바꾸는 공격문은 포함하지 않도록 작성했다. 최종 정상성은 사람이 확인한다.

전체 길이 구성은 본문 100–239자 40건, 240–499자 40건, 500–900자 20건이다. 공백과 줄바꿈을 포함한 Python 문자열 길이를 사용하며 토큰 수를 뜻하지 않는다. 한국어 80건, 한국어·영어 혼합 20건이고 각 유형에 회신 이력 형태를 4건 이상 포함한다. 길이·언어·난이도·형식은 서로 중첩되는 속성이다. 첨부파일·외부 URL·OCR 없이 본문만으로 이해할 수 있다.

생성은 이 대화의 ChatGPT 보조 에이전트들이 유형별로 독립 작성했다. 실제 배포 요약기의 출력으로 정답을 만들지 않았으며, 외부 모델 API를 호출하지 않았다. 정확한 생성 모델 ID·샘플링 설정은 기록할 수 없어 `manifest.json`에 null로 명시했다. 원문, 요약 초안, 사실 체크리스트를 같은 AI 작업 과정에서 만들었으므로 상관된 오류가 남을 수 있다. 독립적인 인간 검토가 필요하다.

## 레코드 의미

- `title`, `body`: 평가 입력이 될 제목과 원문.
- `reference`: 원문만으로 작성한 **기준 요약 초안**. 유일한 정답 문장이 아니다.
- `requiredFacts`: 요약이 보존해야 할 3–6개 핵심 사실. 표현이 달라도 의미가 같으면 인정하는 검토 체크리스트이며, 문자열 완전 일치 규칙이 아니다.
- `factEvidence`: 각 핵심 사실을 뒷받침하는 원문 인용. 같은 인덱스의 `requiredFacts`에 대응한다. 원문에 인용이 존재한다는 것만으로 사실이 올바르게 해석됐음을 보장하지 않는다.
- `expectedLabel`, `reviewStatus`: 생성 목표 라벨과 정상성 검토 상태.
- `referenceReviewStatus`: 요약 초안의 별도 검토 상태.
- `provenance`, `category`, `difficulty`, `language`, `lengthBand`, `format`: 출처 및 표본 구성 메타데이터.
- `reviewNotes`: 변경 전후 정보·예외·부정 표현·오탐 가능 표현 등 사람이 특히 확인할 부분.

## 팀 검토와 확정 절차

1. 유형별 `review/` 문서를 열고, 각 메일이 실제로 정상 업무에 해당하는지 확인한다.
2. 날짜·시간·수량·금액의 일관성, 취소/변경 후 최종 상태, 조건과 예외를 원문과 대조한다. 실제 개인을 식별할 정보나 비밀 값이 없는지도 확인한다.
3. 기준 요약과 필수 정보에 원문에 없는 추론, 과거 정보의 오인, 중요한 행동/기한 누락이 없는지 검토한다. 작성자와 다른 팀원이 검토하는 것을 권장한다.
4. 중복·부자연스러운 문장을 수정하고, 검토자·검토일·판정·수정 이유를 남긴다. 체크박스나 AI의 검사 통과만으로 인간 검토 완료를 선언하지 않는다.
5. 승인된 항목을 별도의 확정 버전으로 묶고 새 데이터 해시를 부여한다. 현재 draft 원본과 검토 이력을 보존한다.

현재 앱의 정상 데이터 ‘검토 완료’는 정상 라벨 승인이고, 기준 요약 테이블의 승인과는 별개다. 정상 입력의 오차단 평가와 요약 품질 평가는 각각 라벨/사실 체크리스트를 사용해 구분한다. 요약 품질 자동 채점 기능이 이 데이터 파일 추가로 구현되지는 않는다.

## 평가할 때

- 방어 규칙·프롬프트 조정용 예시는 별도로 만들고, 최종 평가용 100건을 보면서 규칙을 맞추지 않는다. 아직 이 후보 세트는 확정 평가 세트가 아니다.
- 확정 후에는 방어 OFF/ON에 동일한 이메일, 모델, 생성 설정을 사용한다. 매번 새로 생성하지 않는다.
- 날짜/수량 등 핵심 사실 보존, 없는 사실 추가, 정상 응답 거부, Gateway 오차단, API 오류를 구분한다. API 오류를 오차단이나 공격 실패로 섞지 않는다.
- 반복 실행 횟수를 늘려도 독립 이메일 종류가 늘어나는 것은 아니다. 이메일 수와 실행 수를 따로 기록한다.
- 결과는 **사람이 검토한 합성 이메일 세트에서의 결과**로 보고한다. 이 설계 표본의 비율을 실제 사용자 전체의 오탐률이나 일반적인 요약 성능으로 해석하지 않는다.

## 로컬 확인

저장소 루트에서 Python 3.11 이상으로 실행한다. 외부 패키지가 필요 없으며 네트워크/DB/모델을 사용하지 않는다.

```bash
python datasets/ground_truth_set/v1/validate.py
```

검사 범위는 구조, 100개 고유 ID, 유형·길이·언어·난이도 메타데이터의 값/분포, 동일 본문·제목, 유사 본문 후보, ISO 형식(YYYY-MM-DD) 날짜의 유효성, 원문 근거 인용, 연락처/비밀 값과 유사한 일부 형식, 파일 해시다. 의미 오류·개인정보·공격성·현실 대표성의 완전한 탐지기는 아니다. 초안 수정 후에는 `manifest.json`의 SHA-256과 검사 기록을 함께 갱신한다.

## 운영 등록

`emails.json`은 검토용 확장 스키마이며 현재 웹의 **JSON 가져오기 형식이 아니다**. 자동 seed에는 포함하지 않는다. 명시적으로 실행하는 `scripts/import-ground-truth.py`가 기존 정상 이메일 API에 등록하며, 기본 실행은 읽기 전용 사전 검사다.

등록 시 `title`, `body`, `reference`, `requiredFacts`, `reviewStatus`를 현행 정상 이메일 API에 대응시킨다. 서버가 자체 ID와 버전을 부여하므로 `GT-SYN-*` ID와 DB ID의 대응을 등록 보고서에 보관한다. 유형·난이도·근거 문구 등의 추가 메타데이터는 이 원본 데이터 세트에 보존한다. 인간 검토를 하지 않은 항목은 계속 검토 대기로 등록하고, 기준 요약은 서버의 기존 저장 규칙에 따라 draft로 저장한다.
